# Receipts API

Сервис учёта покупок. Принимает чек со списком позиций, сохраняет в PostgreSQL,
позволяет привязывать позиции к категориям трат и считает расхождение между
суммой позиций и заявленным в чеке итогом.

Это решение позволяет справиться с проблемой ручного учёта расходов: вместо того чтобы вносить данные о покупках в электронную таблицу, можно отправлять их в API для последующего анализа.

## Стек

Python 3.12, FastAPI, PostgreSQL, Redis, psycopg 3, Pydantic, Alembic, Docker, pytest.

## Запуск

```bash
git clone https://github.com/lgdtodaoxiao8/receipts_api.git
cd receipts_api
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
docker compose up -d
alembic upgrade head
fastapi dev api.py
```

`docker compose` поднимает две базы, рабочую на порту 5432 и тестовую на 5433, и Redis на 6379. Таблицы в базах создаёт Alembic, адреса базы и Redis читаются из файла `.env`. Для разбора чеков из текста нужен ключ OpenAI, он тоже читается из `.env`. Остальные эндпоинты работают без него. Шаблон лежит в `.env.example`, достаточно скопировать его и при необходимости поправить под себя.

Документация API после запуска: http://127.0.0.1:8000/docs

## Тесты

```bash
pip install -r requirements-dev.txt
DATABASE_URL="postgresql://postgres:secret@localhost:5433/receipts_test" alembic upgrade head
pytest
```

Адрес тестовой базы указывается явно, потому что в `.env` лежит рабочая, а схему нужно накатить в обе. Сами тесты берут адрес из `pytest.ini` и в рабочую базу не попадают.

Тесты покрывают успешные сценарии, валидацию входных данных, коды ошибок, пагинацию, работу с категориями и расчёт расхождений. Перед каждым тестом таблицы очищаются, а вместе с ними и кеш: он живёт в отдельной базе Redis, так что рабочий не задевается. Поэтому порядок выполнения и повторные запуски на результат не влияют.

## API

| Метод | Путь | Описание |
|-------|------|----------|
| POST | /receipts/parse | Разобрать текст чека в структуру |
| POST | /receipts | Создать чек |
| GET | /receipts | Список чеков с пагинацией |
| GET | /receipts/{id} | Чек по идентификатору |
| POST | /categories | Создать категорию |
| GET | /categories | Список категорий |
| GET | /ping | Проверка работоспособности |

Коды ответов: 422, если данные не прошли валидацию или текст не удалось разобрать как чек, 404 на несуществующий чек, 409 при попытке завести категорию с уже занятым именем, 400, если позиция ссылается на категорию, которой нет, и 503, если сервис модели недоступен.

## Примеры

Разбор текста. Сервис отправляет текст в языковую модель вместе со списком существующих категорий и возвращает структуру, ничего не сохраняя: клиент сначала проверяет результат, а потом отправляет его обычным `POST /receipts`. Категорию модель выбирает только из переданного списка, а если ни одна не подходит, ставит null.

```json
POST /receipts/parse

{
  "text": "магнум\nмолоко 450\nхлеб 200\nитого 650"
}
```

```json
200 OK

{
  "shop": "магнум",
  "total": "650",
  "items": [
    {"name": "молоко", "price": "450", "category_id": 1},
    {"name": "хлеб", "price": "200", "category_id": 2}
  ]
}
```

Если текст не похож на чек, придёт 422. Если сервис модели не ответил, 503.

Создание чека. Поле `category_id` у позиции необязательное: его можно указать или оставить пустым. Базовый набор категорий заливается миграцией при первом запуске, свои добавляются через `POST /categories`.

```json
POST /receipts

{
  "shop": "Магнум",
  "total": 650,
  "items": [
    {"name": "молоко", "price": 450, "category_id": 1},
    {"name": "хлеб", "price": 200}
  ]
}
```

В ответ приходит сохранённый чек. Вместо идентификатора категории подставляется её название, а рядом с заявленным итогом появляются два вычисляемых поля: `calculated_total` — сумма позиций, и `discrepancy` — разница между ней и итогом. Положительное значение означает, что позиции в сумме дороже, чем написано в чеке.

```json
201 Created

{
  "id": 1,
  "shop": "Магнум",
  "total": "650.00",
  "purchased_at": "2026-09-26T19:12:03.481220Z",
  "items": [
    {"name": "молоко", "price": "450.00", "category_name": "еда"},
    {"name": "хлеб", "price": "200.00", "category_name": null}
  ],
  "calculated_total": "650.00",
  "discrepancy": "0.00"
}
```

Если итог в чеке не указан, `discrepancy` будет `null`: сравнивать не с чем.

Список чеков отдаётся страницами, размер и сдвиг задаются параметрами `limit` и `offset`. По умолчанию это двадцать чеков с начала, самые свежие сверху.

```
GET /receipts?limit=20&offset=0
```

## Схема данных

Три таблицы. `receipts` хранит чек: время покупки, магазин, заявленный итог.
`items` хранит позиции, ссылается на чек и опционально на категорию.
`categories` хранит справочник категорий трат.

Позиции читаются через `LEFT JOIN` с категориями, поэтому товар без категории из ответа не пропадает, у него просто пустое `category_name`.

Справочник категорий наполняется миграцией при развёртывании: шестнадцать категорий, покрывающих обычный чек из магазина. Их можно удалять и дополнять через API, разбор текста работает с тем, что есть в базе на момент запроса.

## Технические решения

**NUMERIC вместо float для денег.** Тип `float` хранит числа в двоичном представлении, и некоторые десятичные дроби невозможно точно выразить в этом формате. Это приводит к классическому результату: `0.1 + 0.2 = 0.30000000000000004`. Хотя это может показаться несущественным, при обработке потока транзакций такие расхождения накапливаются, превращаясь в заметную погрешность. Тип `NUMERIC` обеспечивает точное хранение десятичных чисел.

**Два запроса вместо JOIN при чтении списка.** Самый простой подход, это запросить список чеков, а затем в цикле запрашивать товарные позиции для каждого из них; для двадцати чеков это выливается в двадцать один запрос к базе данных. Так называемая проблема N+1. В данном же случае выполняются всего два запроса независимо от количества чеков: сначала запрашиваются сами чеки, а потом товарные позиции для всех этих чеков сразу, с использованием оператора `ANY`, после чего в Python выполняется группировка по `receipt_id`. Использование одного запроса с `JOIN` здесь тоже не подходит: данные чека дублировались бы в каждой строке, а вложенную структуру пришлось бы собирать вручную.

**TIMESTAMPTZ вместо TIMESTAMP.** Этот тип данных сохраняет момент времени в формате UTC, а возвращает его в часовом поясе запрашивающей стороны. Тип TIMESTAMP просто хранит показания часов без привязки к часовому поясу; в результате два момента времени из разных часовых поясов становятся неразличимыми, а сортировка по времени может работать некорректно.

**Валидация на двух уровнях.** Pydantic отсекает некорректные данные на границе API и возвращает клиенту 422 с указанием конкретного поля. Ограничения CHECK в базе гарантируют, что мусор не попадёт в таблицы никаким путём, включая запись из скрипта или psql напрямую.

**Пул соединений.** Установление соединения с Postgres занимает десятки миллисекунд, тогда как выполнение самого запроса около миллисекунды. Это означает, что почти всё время отклика уходило бы именно на установку соединения, а при высокой нагрузке база данных не справилась бы с потоком новых процессов. Пул поддерживает набор готовых соединений: запрос берёт свободное, выполняет задачу и возвращает его обратно.

**Границы отказа внешнего сервиса.** Обращение к языковой модели может сорваться по-разному: таймаут, превышение лимита запросов, сбой на их стороне, ответ в неожиданном формате. Все эти случаи переводятся в два собственных исключения: одно означает, что текст не удалось разобрать, второе что сервис недоступен. Для клиента это превращается в 422 и 503 соответственно, и он понимает кто виноват и стоит ли повторять запрос. Сам запрос выполняется асинхронно, позволяя обработчику обслуживать другие запросы пока ждет ответ от сервиса модели.

**Категории выбираются из справочника существующих.** Если позволить модели называть категорию свободно, справочник заполнится синонимами по типу еда, продукты, питание, продукты питания, и статистика по ним окажется неинформативной. Поэтому в запрос передаётся список существующих категорий, и модель выбирает только из них. Позиция, для которой ни одна категория не подошла, остаётся без категории вовсе: отдельная запись «прочее» была бы неотличима от случая, когда определить не удалось.

**Кеширование разбора.** Обращение к модели стоит денег и занимает несколько секунд, а один и тот же текст разбирается всегда одинаково. Результат кладётся в Redis на сутки, ключом служит хеш от текста вместе со списком категорий: если справочник изменился, прежний разбор уже не годится, в нём остались старые идентификаторы. Срок жизни нужен по другой причине — промпт и модель со временем меняются, и запись, лежащая вечно, однажды начнёт отдавать разбор по правилам, которых в коде давно нет. Кеш при этом не обязателен для работы: если Redis недоступен, сервис просто идёт в модель и отвечает медленнее.
