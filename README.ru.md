# Receipts API

Сервис учёта покупок. Принимает чек со списком позиций, сохраняет в PostgreSQL,
позволяет привязывать позиции к категориям трат и считает расхождение между
суммой позиций и заявленным в чеке итогом.

Это решение позволяет справиться с проблемой ручного учета расходов: вместо того чтобы вносить данные о покупках в электронную таблицу, можно отправлять их в API для последующего анализа.

## Стек

Python 3.12, FastAPI, PostgreSQL, psycopg 3, Pydantic, Alembic, Docker, pytest.

## Запуск

```bash
git clone <url>
cd receipts
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
docker compose up -d
DATABASE_URL="postgresql://postgres:secret@localhost:5432/receipts" alembic upgrade head
fastapi dev api.py
```

Документация API после запуска: http://127.0.0.1:8000/docs

## Тесты

```bash
DATABASE_URL="postgresql://postgres:secret@localhost:5433/receipts_test" alembic upgrade head

```

расчёт расхождений.

## API

| Метод | Путь | Описание |
|-------|------|----------|
| POST | /receipts | Создать чек |
| GET | /receipts | Список чеков с пагинацией |
| GET | /receipts/{id} | Чек по идентификатору |
| POST | /categories | Создать категорию |
| GET | /categories | Список категорий |
| GET | /ping | Проверка работоспособности |

## Схема данных

Три таблицы. `receipts` хранит чек: время покупки, магазин, заявленный итог.
`items` хранит позиции, ссылается на чек и опционально на категорию.
`categories` хранит справочник категорий трат.

## Технические решения

**NUMERIC вместо float для денег.** Тип `float` хранит числа в двоичном представлении, и некоторые десятичные дроби невозможно точно выразить в этом формате. Это приводит к классическому результату: `0.1 + 0.2 = 0.30000000000000004`. Хотя это может показаться несущественным, при обработке потока транзакций такие расхождения накапливаются, превращаясь в заметную погрешность. Тип `NUMERIC` обеспечивает точное хранение десятичных чисел.

**Два запроса вместо JOIN при чтении списка.** Самый простой подход, это запросить список чеков, а затем в цикле запрашивать товарные позиции для каждого из них; для двадцати чеков это выливается в двадцать один запрос к базе данных. Так называемая проблема N+1. В данном же случае выполняются всего два запроса независимо от количества чеков: сначала запрашиваются сами чеки, а потом товарные позиции для всех этих чеков сразу, с использованием оператора `ANY`, после чего в Python выполняется группировка по `receipt_id`. Использование одного запроса с `JOIN` здесь тоже не подходит: данные чека дублировались бы в каждой строке, а вложенную структуру пришлось бы собирать вручную.

**TIMESTAMPTZ вместо TIMESTAMP.** Этот тип данных сохраняет момент времени в формате UTC, а возвращает его в часовом поясе запрашивающей стороны. Тип TIMESTAMP просто хранит показания часов без привязки к часовому поясу; в результате два момента времени из разных часовых поясов становятся неразличимыми, а сортировка по времени может работать некорректно.

**Валидация на двух уровнях.** Pydantic отсекает некорректные данные на границе API и возвращает клиенту 422 с указанием конкретного поля. Ограничения CHECK в базе гарантируют, что мусор не попадёт в таблицы никаким путём, включая запись из скрипта или psql напрямую.

**Пул соединений.** Установление соединения с Postgres занимает десятки миллисекунд, тогда как выполнение самого запроса около пары миллисекунд. Это означает, что 95% времени уходит именно на установку соединения. Пул соединений поддерживает набор готовых соединений: запрос берет свободное соединение, выполняет задачу и возвращает его обратно в пул. Без использования пула почти всё время отклика уходило бы на процесс установления соединения, а при высокой нагрузке база данных не справилась бы с потоком новых процессов.
