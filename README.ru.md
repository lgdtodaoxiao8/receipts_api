# Receipts API

Сервис учёта покупок. Принимает чек со списком позиций и сохраняет его в PostgreSQL. Позиции можно привязать к категориям трат, а сервис сам считает, сходится ли сумма позиций с итогом, который написан в чеке. Текст чека можно не разбирать руками: его разберёт языковая модель.

Каждый пользователь видит только свои чеки. Вход по email и паролю, дальше запросы идут с JWT-токеном.

Идея простая: вместо таблицы, куда покупки вносятся вручную, чеки отправляются в API, а потом по ним строится сводка трат по категориям.

## Стек

Python 3.12, FastAPI, PostgreSQL, Redis, psycopg 3, Pydantic, Alembic, PyJWT, argon2, Docker, pytest.

## Запуск

```bash
git clone https://github.com/lgdtodaoxiao8/receipts_api.git
cd receipts_api
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
docker compose up -d
alembic upgrade head
fastapi dev api.py
```

`docker compose` поднимает две базы, рабочую на порту 5432 и тестовую на 5433, и Redis на 6379. Таблицы создаёт Alembic. Адреса базы и Redis приложение берёт из `.env`, шаблон лежит в `.env.example`.

Перед первым запуском в `.env` нужно заполнить `JWT_SECRET`, этим ключом подписываются токены. Пустым его оставлять нельзя: токен с пустым ключом подделает кто угодно. Сгенерировать ключ можно так:

```bash
python -c "import secrets; print(secrets.token_urlsafe(32))"
```

Для разбора чеков из текста нужен ключ OpenAI в `OPENAI_API_KEY`. Остальное работает без него.

Документация API после запуска: http://127.0.0.1:8000/docs

## Авторизация

Сначала регистрация:

```json
POST /auth/register

{
  "email": "user@mail.com",
  "password": "my-password"
}
```

```json
201 Created

{"id": 1, "email": "user@mail.com"}
```

Потом вход с теми же данными:

```json
POST /auth/login

{
  "email": "user@mail.com",
  "password": "my-password"
}
```

```json
200 OK

{"access_token": "eyJhbGciOi...", "token_type": "bearer"}
```

Дальше токен передаётся в заголовке каждого запроса:

```
Authorization: Bearer eyJhbGciOi...
```

Токен живёт 15 минут, потом нужно войти заново. `GET /me` возвращает id и email того, чей это токен.

Email приводится к нижнему регистру, так что `User@Mail.com` и `user@mail.com` это один аккаунт. Email не длиннее 100 символов, пароль от 8 до 128.

В Swagger у защищённых эндпоинтов есть поле `authorization`. В него вписывается строка целиком, вместе со словом `Bearer`.

## API

| Метод | Путь | Описание | Нужен токен |
|-------|------|----------|-------------|
| POST | /auth/register | Регистрация | нет |
| POST | /auth/login | Вход, выдаёт токен | нет |
| GET | /me | Текущий пользователь | да |
| POST | /receipts/parse | Разобрать текст чека в структуру | да |
| POST | /receipts | Создать чек | да |
| GET | /receipts | Свои чеки с пагинацией | да |
| GET | /receipts/stats | Сводка своих трат по категориям за период | да |
| GET | /receipts/{id} | Свой чек по идентификатору | да |
| POST | /categories | Создать категорию | да |
| GET | /categories | Список категорий | нет |
| GET | /ping | Проверка, что сервис жив | нет |

Коды ответов:

- 401: нет токена, токен битый или истёк, неверный email или пароль при входе, пользователь из токена больше не существует;
- 404: чека нет или он принадлежит другому пользователю;
- 409: email уже зарегистрирован или категория с таким именем уже есть;
- 400: позиция ссылается на категорию, которой нет;
- 422: данные не прошли валидацию, текст не удалось разобрать как чек, границы периода заданы без часового пояса или конец раньше начала;
- 503: сервис модели недоступен.

## Примеры

Все запросы ниже отправляются с заголовком `Authorization`.

Разбор текста. Сервис отправляет текст в языковую модель вместе со списком существующих категорий и возвращает структуру. Сохранять он ничего не сохраняет: клиент сначала смотрит на результат и потом отправляет его обычным `POST /receipts`. Категорию модель берёт только из переданного списка. Если ни одна не подходит, ставит null.

```json
POST /receipts/parse

{
  "text": "магнум\nмолоко 450\nхлеб 200\nитого 650"
}
```

```json
200 OK

{
  "shop": "магнум",
  "total": "650",
  "items": [
    {"name": "молоко", "price": "450", "category_id": 1},
    {"name": "хлеб", "price": "200", "category_id": 2}
  ]
}
```

Если текст не похож на чек, придёт 422. Если сервис модели не ответил, 503.

Создание чека. `category_id` у позиции можно не указывать. Базовый набор категорий заливается миграцией при первом запуске, свои добавляются через `POST /categories`. Время покупки передаётся в `purchased_at`, обязательно с часовым поясом. Если его не передать, подставится время создания записи, так что для чеков за прошлые дни его лучше указывать.

Владельца чека в запросе указывать не нужно, сервис берёт его из токена.

```json
POST /receipts

{
  "shop": "Магнум",
  "total": 650,
  "purchased_at": "2026-09-26T19:12:03Z",
  "items": [
    {"name": "молоко", "price": 450, "category_id": 1},
    {"name": "хлеб", "price": 200}
  ]
}
```

В ответ приходит сохранённый чек. Вместо id категории в нём стоит её название, а рядом с итогом из чека два вычисляемых поля: `calculated_total`, сумма позиций, и `discrepancy`, разница между этой суммой и итогом. Если `discrepancy` больше нуля, позиции вместе стоят дороже, чем написано в чеке.

```json
201 Created

{
  "id": 1,
  "shop": "Магнум",
  "total": "650.00",
  "purchased_at": "2026-09-26T19:12:03Z",
  "items": [
    {"name": "молоко", "price": "450.00", "category_name": "еда"},
    {"name": "хлеб", "price": "200.00", "category_name": null}
  ],
  "calculated_total": "650.00",
  "discrepancy": "0.00"
}
```

Если итога в чеке нет, `discrepancy` будет `null`, сравнивать не с чем.

Список чеков отдаётся страницами, размер и сдвиг задаются через `limit` и `offset`. По умолчанию это двадцать последних чеков, самые свежие сверху.

```
GET /receipts?limit=20&offset=0
```

Сводка трат. Группирует позиции по категориям за период и сортирует по сумме. Границы можно не указывать, тогда считается всё время.

```
GET /receipts/stats?period_start=2026-09-01T00:00:00Z&period_end=2026-10-01T00:00:00Z
```

```json
200 OK

[
  {"category_name": "еда", "total_expenses": "12400.00", "items_count": 23},
  {"category_name": "напитки", "total_expenses": "3200.00", "items_count": 8},
  {"category_name": null, "total_expenses": "750.00", "items_count": 3}
]
```

Начало периода входит в выборку, конец нет. Так соседние периоды не пересекаются, и чек на стыке не посчитается дважды. Позиции без категории идут отдельной строкой с `category_name` равным `null`.

## Схема данных

Четыре таблицы:

- `users`: email (уникальный), хэш пароля, время регистрации;
- `receipts`: чек, то есть владелец, время покупки, магазин и итог;
- `items`: позиции чека, ссылаются на чек и, если указана, на категорию;
- `categories`: справочник категорий, общий для всех пользователей.

Позиции читаются через `LEFT JOIN` с категориями, поэтому позиция без категории из ответа не пропадает, у неё просто пустое `category_name`.

Справочник категорий заполняется миграцией: шестнадцать категорий, которых хватает на обычный чек из магазина. Новые добавляются через API, а разбор текста работает с тем набором, который есть в базе в момент запроса.

## Технические решения

**Пароли хранятся только как хэш argon2.** Сам пароль нигде не сохраняется. Argon2 специально считается медленно и требует много памяти, поэтому перебирать пароли по утёкшей базе долго и дорого. Хэш никогда не уходит в ответах API: для данных пользователя есть отдельная модель ответа, где его просто нет.

**JWT вместо сессий.** В токене лежит id пользователя и время, когда токен истекает. Сверху стоит подпись секретным ключом. Чтобы проверить запрос, серверу достаточно проверить подпись, в базу ходить не нужно. Минус JWT в том, что выданный токен нельзя отозвать до конца его срока. Поэтому срок короткий, 15 минут.

**Владелец чека берётся из токена.** В теле запроса поля `user_id` нет. Если бы оно было, любой мог бы подставить чужой id и создать чек от чужого имени. Сервер сам достаёт id из подписанного токена, и клиент на это повлиять не может.

**Чужой чек отдаёт 404, а не 403.** Ответ 403 сказал бы «такой чек есть, но он не твой», то есть подтвердил бы, что чек существует. Перебирая id, можно было бы узнать, сколько чеков в системе. А 404 одинаковый для чужого и несуществующего чека, по нему ничего не понять. Каждый запрос к чекам фильтруется по `user_id` прямо в SQL, так что до чужих данных код даже не доходит.

**Одинаковый ответ на неверный email и неверный пароль.** Если отвечать «такого email нет» и «пароль неверный» по-разному, можно проверить, зарегистрирован ли конкретный человек. Поэтому в обоих случаях приходит одно и то же: 401 «неверный email или пароль».

**Отдельные модели для регистрации и входа.** При регистрации пароль проверяется на длину от 8 до 128 символов. При входе проверяется только верхний предел. Если бы вход проверял и минимальную длину, на короткий пароль приходил бы 422, а не 401, и ответ подсказывал бы правила паролей. Верхний предел нужен везде: argon2 считается долго, и пароль на несколько мегабайт надолго занимал бы сервер.

**Какой внешний ключ нарушен, видно по имени ограничения.** При создании чека база может отказать по двум причинам: нет такой категории или нет такого пользователя (например, его удалили, а токен ещё действует). Postgres сообщает, какое именно ограничение не выполнено, и по его имени сервис отвечает 400 в первом случае и 401 во втором.

**NUMERIC вместо float для денег.** `float` хранит числа в двоичном виде, и часть десятичных дробей в нём точно не записывается. Отсюда классическое `0.1 + 0.2 = 0.30000000000000004`. На одном чеке это незаметно, но на потоке операций ошибка копится. `NUMERIC` хранит десятичные числа точно.

**Два запроса вместо N+1 при чтении списка.** Если сначала получить чеки, а потом в цикле запрашивать позиции каждого, на двадцать чеков уйдёт двадцать один запрос к базе. Здесь запросов всегда два: сначала чеки, потом позиции всех этих чеков сразу через `ANY`, а по чекам они раскладываются уже в Python. Один запрос с `JOIN` тоже не подходит: данные чека повторялись бы в каждой строке, и вложенную структуру всё равно пришлось бы собирать руками.

**TIMESTAMPTZ вместо TIMESTAMP.** `TIMESTAMPTZ` хранит момент времени в UTC и отдаёт его в нужном часовом поясе. `TIMESTAMP` хранит просто цифры на часах без пояса, и два момента из разных поясов становятся неотличимы. Поэтому и время покупки, и границы периода принимаются только с явным часовым поясом. Иначе база подставила бы пояс из настроек соединения, и результат зависел бы от того, как настроен сервер.

**Валидация на двух уровнях.** Pydantic отсекает плохие данные на входе в API и возвращает 422 с указанием поля. Ограничения `CHECK` в базе не пускают мусор в таблицы, даже если писать в них в обход API, скриптом или через psql.

**Пул соединений.** Открыть соединение с Postgres стоит десятки миллисекунд, а сам запрос выполняется примерно за одну. Если открывать соединение на каждый запрос, почти всё время ответа уходило бы на это, а под нагрузкой база захлебнулась бы новыми процессами. Пул держит готовые соединения: запрос берёт свободное, делает своё и возвращает его обратно.

**Сбои языковой модели.** Запрос к модели может не пройти по разным причинам: таймаут, превышен лимит, ошибка на их стороне, ответ в неожиданном формате. Всё это сводится к двум своим исключениям: «текст не удалось разобрать» и «сервис недоступен». Клиент получает 422 или 503 и понимает, есть ли смысл повторить запрос. Сам запрос к модели асинхронный, так что пока сервис ждёт ответа, он обслуживает другие запросы.

**Категории только из справочника.** Если разрешить модели называть категорию как угодно, справочник зарастёт синонимами вроде «еда», «продукты», «питание», и статистика по ним развалится. Поэтому модель получает список существующих категорий и выбирает только из него. Если ничего не подошло, позиция остаётся без категории. Отдельная категория «прочее» была бы неотличима от случая, когда модель просто не справилась.

**Кэш разбора.** Запрос к модели стоит денег и занимает несколько секунд, а один и тот же текст разбирается одинаково. Результат кладётся в Redis на сутки, ключ это хэш от текста вместе со списком категорий: если справочник поменялся, старый разбор уже не годится, в нём старые id. Срок жизни нужен по другой причине: промпт и модель со временем меняются, и вечная запись однажды начала бы отдавать разбор по правилам, которых в коде уже нет. Без Redis сервис тоже работает, просто каждый раз идёт в модель и отвечает медленнее.

**Индексы.** Сводка отбирает чеки по `purchased_at`, по нему же сортируется список, а все запросы к чекам фильтруются по `user_id`. На обе колонки стоят индексы. Без них база читала бы таблицу целиком и проверяла каждую строку. На тысяче чеков это незаметно, на миллионе это секунды. Цена индекса это место на диске и чуть более медленная вставка.

## Тесты

```bash
pip install -r requirements-dev.txt
DATABASE_URL="postgresql://postgres:secret@localhost:5433/receipts_test" alembic upgrade head
pytest
```

Адрес тестовой базы в команде указан явно, потому что в `.env` лежит рабочая, а схему нужно накатить в обе. Сами тесты берут адрес базы, Redis и тестовый `JWT_SECRET` из `pytest.ini` и в рабочую базу не попадают.

Что проверяется:

- создание и чтение чеков, пагинация, категории, расчёт расхождений, сводка за период;
- валидация входных данных и коды ошибок;
- разбор текста, причём модель в тестах подменена, и в OpenAI тесты не ходят;
- регистрация, вход, `/me`, повторный email в любом регистре, длина email и пароля на границе и на шаг за ней;
- что хэш пароля не попадает ни в один ответ;
- что каждый защищённый эндпоинт без токена отвечает 401;
- битые токены: мусор вместо токена, токен с изменённым символом, токен с чужим ключом, без `sub` и с нечисловым `sub`, а также истёкший токен и неправильный заголовок;
- что пользователь не видит чужой чек ни по id, ни в списке, ни в сводке.

Перед каждым тестом таблицы и кэш очищаются, кэш при этом живёт в отдельной базе Redis. Перед каждым тестом также автоматически создаётся пользователь, и его токен подставляется в запросы. Тесты, которым он мешает, помечены `@pytest.mark.no_auth`. Порядок запуска и повторные запуски на результат не влияют.

В CI на каждый пуш запускаются ruff, mypy, миграции и все тесты.

## Планы

- Refresh-токены, чтобы не входить заново каждые 15 минут, и выход с отзывом токена.
- Изменение и удаление чеков.
- Ограничение частоты попыток входа и запросов к модели.
- Запуск всего сервиса одной командой через Docker.
